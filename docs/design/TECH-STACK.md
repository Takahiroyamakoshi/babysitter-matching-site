## 1. 結論から読む

**画面は既存の TypeScript / React / Vite を継続し、公開用データ基盤は Supabase Pro の PostgreSQL・Auth・Storage・Edge Functions に集約する案を推奨する。画面は Cloudflare Workers Static Assets の無料静的配信、取引メールは Amazon SES の従量課金。決済の第一候補は Stripe Connect の直接決済だが、費用・損失負担と日本での契約適合を確認するまで確定しない。**

月300予約のソフトウェアは、1米ドル150円・税込相当10%の仮定で **月4,400〜4,900円を設計枠** とする。AIは別に月1,000円以内。これは実見積りではなく、為替・容量・送信数・契約で超える可能性がある。第5章で積算する。人件費、決済手数料、事業保険・税務等はこの枠に含めない。

予約・延長・異議・支払いを一貫して扱えるトランザクション、管理者MFA、非公開添付、バックアップを少数のサービスで揃え、シッター手取りを減らす運用負担を抑えるための選定。Cloudflare D1は不可能だから除外するのではない。安い基盤費と引換えに、認証の組合せ・競合制約・復旧・情報取扱いを個別検証する負担が増えるため、全業務を揃える第一案にはしない。

通常のレンタルサーバーはWebページやDBを置く場所を借りる方式。VPSはOSから管理するサーバーを借りる方式。今回の管理型クラウドはログイン・DB・ファイル・APIを部品として借り、基盤更新等を事業者へ任せる。アプリの権限・データ・通知・復元確認は運営側に残る。サーバー月額だけで総コストを比較しない。

## 2. 選ぶ部品と役割

| 部分 | 推奨 | 理由・採用条件 |
|---|---|---|
| 言語 | TypeScript（画面/API/共通料金規則）とSQL（DB整合性） | 既存UIを利用し業務型を共有。API入力は実行時にも検査 |
| フロント | React + Vite + React Router、標準CSS | 既存資産を継続。役割別URL、戻る/再読み込み、エラー回復を整える |
| 画面配信 | Cloudflare Workers Static Assets Free | HTML/JS/CSSのみ。個人データを成果物・公開キャッシュへ入れない |
| API/実行環境 | Supabase Edge FunctionsのDeno/TypeScript、HTTPS JSON | 権限・計算・外部連携。Node HTTP/fsをそのまま移植しない |
| DB | Supabase Pro・Tokyo PostgreSQL、SQL migration | 承認/変更/延長をDB transactionと制約・排他で保護 |
| 認証 | Supabase Auth（メール認証/回復）、運営TOTP MFA必須 | 資格確認・決済KYCと別管理。本人編集属性で権限判定しない |
| 添付 | Supabase Storage private bucketを用途別分離 | 資格等・チャット・事故で異なる権限。短期URLも漏洩を想定 |
| 期限/通知 | PostgreSQL outbox + Cron + 短時間Edge worker | 状態と通知予約を一体保存。再試行で重複させない |
| メール | Amazon SES、アプリHTTPS API / Auth custom SMTP | 無料枠に依存しない少量従量。ドメイン・quota・失敗を確認 |
| 決済 | Stripe Connect直接決済 + Stripe提供onboarding/外部カード入力 | シッター85%+実費、運営15%から処理費。損失責任等は第6章 |
| AI | OpenAI API gpt-6-luna評価候補 + サーバーadapter/schema/予算台帳 | 自己紹介/公開FAQ/不備案内だけ。モデルは第7章 |
| 検索/チャット | PostgreSQL索引検索、表示中の差分ポーリング | 専用検索・Realtimeを初期必須にせず負荷実測 |
| 監視 | 事業者標準ログ + DB業務監視/予算台帳 | 予約失敗・outbox滞留・決済不一致・事故・backup失敗を優先 |
| backup | DB日次 + Storage原本の別コピー | DBだけでは添付が戻らない。権限も含め実復元 |
| 開発/試験 | 対応Node LTSでVite build、node:test継続、Deno/SQL統合、Playwright重要E2E | 合成/local Supabaseから。外部実証は別許可 |
| 版管理 | 明示バージョン+lock、migration/API/規則版 | 現行latest指定は後続で固定。npm ci、更新PRと回帰試験 |

React公式は新規開発で統合フレームワークを推奨し、ViteとルーターのSPA構成も説明する。本製品は認証後の操作が中心で既存SPAがあるため、SSR/RSCを目的なく導入する利益は小さいと判断する。公開プロフィールの検索流入が事業指標になったら、そのページの静的生成/SSRだけを再評価。Vite開発サーバーは本番配信に使わない。[React公式](https://react.dev/learn/build-a-react-app-from-scratch)、[Vite公式](https://vite.dev/guide/)

## 3. 利用の流れと責任

~~~text
スマホ → Cloudflare（画面）
       → Supabase Auth（ログイン/回復/MFA）
       → Edge API（本人/権限/入力検査）
            ├ PostgreSQL（依頼/原子承認/同意/実績/異議）
            │    └ outbox/Cron → Webお知らせ / SES / 決済照合
            ├ private Storage（用途別非公開画像）
            ├ Stripe（カード登録/決済/シッターへの入金）
            └ AI adapter（送信許可した最小文章だけ）
~~~

保護者は相手を検索しログインして直接相談。依頼時はサーバーが条件・最新料金・交通費を再計算し、同意版を固定する。シッター承認で受付条件と移動枠までDB内で再検査して成立。利用後は実績を通知し、承認または正しい起算点から24時間後に決済する。異議中は止め、再提出後は明示承認が必要。Stripe署名通知とAPI照合で結果を保存し、画面の自己申告を成功根拠にしない。

ログイン、資格確認、外部入金設定は別状態。運営の独自身分証回収/Stripe Identityを追加しない。事故は各報告者と事故担当だけが閲覧し、相手当事者へ自動共有しない。保険期限30/7/0日前JST9時通知を行い、期限切れによる自動受付停止は追加しない。

## 4. G01で先に固める最小技術契約

G01全体の完成宣言ではない。G03比較/PoCの入力を揃える最小案。全業務の状態/権限/料金/通知対応表はG01で別途完成・監査する。

1. **データ/状態**: 利用者/公開プロフィール、児/住所、審査/根拠、空き枠、会話/添付、依頼、回別予約、料金snapshot/規則版/同意、変更/延長、実績/通知、異議、支払/返金、未払い、レビュー、免除/処分、事故、監査、outbox、冪等操作を別記録とする。予約と支払、決済成功と銀行入金完了も分離。円整数、計算は整数比で保持し合計で切捨て。UTC保存・Asia/Tokyoの暦日/3か月境界。
2. **変更主体**: ブラウザーから予約/支払/審査を任意UPDATEできない。業務APIに集約。Edgeは署名済ログインとDB上の有効利用者/現在権限を検査し、検証済actorをDBへ渡す。DB呼出権限も限定し、ブラウザーが任意actorを指定してRPCを迂回実行できないようにする。Data API GRANTとRLSを別々に監査。secret/service roleをブラウザーへ出さない。退会/処分/権限失効後は古いJWTでも拒否。厳格な操作はsession_idとauth.sessions照合等でlogout/session失効も検査し、運営はserver/DBでaal2を強制する。
3. **原子承認**: 保護者/シッターの安定したDB guard行を全変更経路共通の一定順序で先にロックし、対象依頼・成立予約・調整済移動余裕を同一transactionで検査/更新。時間range制約も防御に追加。延長/日時変更/取消/空き枠/移動余裕変更/未払い発生/審査や受付能力の変更も同じ排他規約を守る。SELECTとUPDATEを別APIへ分けず、一つのDB関数内のtransactionで完結。DB関数は既定SECURITY INVOKER、特権が必要な場合だけ非公開schema・EXECUTE最小化・固定search_pathとactor検査を監査する。移動余裕変更を成立済予約へ無確認で遡及しない。重複2承認は片方だけ成功、隣接間は必要な最大移動余裕を確保。期限・年齢/地域/資格/初回審査/人数/入金準備/未払いも直前検査。
4. **再送/外部作用**: actor+operationIdを一意にし入力fingerprintと結果を保存。同じIDの別内容は拒否。状態とoutboxを一体保存。workerはlease/試行回数/次回時刻/重複キーを持つ。メールの完全な一回配信は保証できないため通知ID/送信IDを照合。決済は事業者冪等key、イベントID一意、署名/生body/account検査、順不同時API照合で収束。
5. **期限/競合**: Cronや画面時計だけに頼らず操作時にも期限検査。依頼は送信24h後と開始の早い方で失効。実績通知成立条件をWeb保存/メール受付・失敗・再試行と対応づけG01で確定し、失敗時に起算しない保守的案をPoC対象とする。異議と決済は同じ実績版をロックし、処理中は事業者へ照合。成功済みを保留へ戻さない。未払いは利用者単位と全予約へ作用し、全残債の成功確認で制限解除、取消は復活しない。既に保育中なら安全な引渡しまで継続し、実施中/済みへの二重取消料を防ぐ。
6. **情報境界**: 公開projectionに原本・保険情報・番地なし。児/住所は本人と選択相手/依頼受信者に必要範囲だけ。原本は本人+審査、事故は報告者+事故担当、決済担当は必要取引情報。URLは検査後短期発行。Storageのオブジェクト名推測や別添付IDでも越権できないことを試す。

## 5. 月額の積算と負荷条件

金額は2026-10-17の公開資料を基礎にした設計試算。**1USD=150円は見積り用の仮定で、取得した実勢為替ではない。全USD費用に10%を加えるのも保守的な試算条件で、各社請求書の税務判定ではない。** 初期は本番1プロジェクト/Micro、開発はlocal。常設有料stagingやPITRを無条件に加えない。

| ソフトウェア | 月額USD/数量前提 | 円概算（税相当込み） |
|---|---|---:|
| Supabase Pro | $25、含有compute creditでMicro1台 | 4,125 |
| Cloudflare静的配信Free | APIを置かず含有範囲 | 0 |
| SES | 4,000受信者分×$0.16/1,000=$0.64 | 106 |
| 添付/DB別backupの保存・操作 | $0.50〜1.50を容量枠として仮置き | 83〜248 |
| ドメイン年額の月割 | 契約先/更新料未確定の予算枠 | 150〜250 |
| 標準監視、local開発 | 含有範囲、専用有料監視は初期追加なし | 0 |
| 送信データ/ログ等の余裕 | 予算枠、測定後更新 | 0〜150 |
| **ソフト計** | 実見積りではない | **4,464〜4,879** |
| **AI別枠** | 第7章、1,000円上限 | **0〜1,000** |

Supabase $25は無制限の全機能料金ではない。DB/ファイル容量・帯域・API/Edge呼出し・MAU・compute・追加プロジェクト・バックアップオプションで変わる。Freeの休止・復旧条件を本番標準にしない。内訳・各quota・Cloudflare/D1/レンタルサーバー比較の一次資料は [基盤調査](../research/TECH-INFRA.md) を参照。別backupの$0.50〜1.50とドメインはベンダー見積りではなく予算割当で、容量・操作・取り出し費をPoC後に積算する。無料枠が終わるときも予算判定が必要。

為替が170円なら同じ$25だけで4,675円となり、メール/backup/ドメイン込みでは5,000円を超え得る。為替・実請求・利用量を月次確認し、50/80/100%で通知。AIはアプリ側で呼出停止できるが、既に発生したクラウド課金や不正トラフィック全体を台帳で絶対に止められるとはしない。rate limit・アップロード上限・事業者quotaを組み合わせる。上限超過はD1へ具体額と削減/増額案を提示し、勝手に有料機能や大きいcomputeへ変更しない。

### メールと認証

月300予約に「依頼/承認、実績/確認・支払、開始/未払い/取消等の双方通知」を含め **平均12通/予約=3,600通**、登録/回復等400通で4,000通を仮定する。12は全予約に必ず同じ通知を送る仕様ではなく、イベント対応表から再積算するための容量モデル。チャット毎通のメール連投をせず、未読新着のまとめ方をG10で決める。保険3回、事故、処分、再送が多い月は別加算する。

日次ピーク例は30予約×12通+認証40通=400通/日。Resend Freeの月3,000/日100通では足りず、SES sandboxの上限も本番運用に十分とはしない。送信ドメイン/SPF/DKIM/DMARC、production accessと日次/秒速quota、bounce/complaint、配信失敗通知を確認する。SES新規地域の現行Essentialsは$0.16/1,000受信者で、旧$0.10のà-la-carte選択を既定としない。大量の広告配信は含めない。[SES料金](https://aws.amazon.com/ses/pricing/)

Supabase Authは標準メールを本番送信基盤とせずcustom SMTPを設定。AuthのMAU枠とメールの送信数・回復/ログイン頻度制限は別。SMSは初期既定にしない。管理者MFAのTOTP/回復方法と、認証/role失効後のセッション拒否を実証する。Authログインを身分証本人確認と説明しない。

### ポーリングとAPI

チャットは表示中15秒の差分取得を初期設計値とする。20人が各2時間/日×30日なら288,000呼出/月。その他API・Cron・再送を含めて計測し、含有Edge呼出数内か確認する。20人が24時間常時開けば3,456,000呼出となるため「同時20人なら必ず無料枠内」とはしない。非表示タブで停止、無操作/障害時の間隔延長、cursor/索引/pagination、不要な全件bootstrap更新を廃止する。期限判定・承認は読取ポーリングに依存しない。長時間接続が必要になった時だけRealtimeへ再評価。

EdgeはDenoで短い入出力処理に限定する。公表のメモリ/CPU/実行時間上限とNode依存の適合を確認する。画像処理をCPU負荷のあるNode用sharpへ無条件移植せず、後述の画像検証PoCで成立しなければ専用処理方式と費用を再設計する。[Edge Functions](https://supabase.com/docs/guides/functions)

## 6. 決済はStripe Connectを条件付き第一候補にする

詳細・公式根拠は [決済調査](../research/TECH-PAYMENTS.md)。Accounts v2の直接決済で、総請求からサービス部分15%だけをapplication feeとし、Stripeの処理費/Connect費は運営が負担する。Stripe提供のhosted/embedded画面に口座・本人確認を任せ、アプリはIDと準備状態を最小保存する。v2のfees_collector=application（v1 controller.fees.payer=application）を明示して検証。旧type=expressだけではapplication_expressとなり、処理費がシッターから引かれるためそのまま採用しない。

サービス6,000円+実費500円なら保護者6,500円、運営fee900円、シッター銀行5,600円を検証する。カード3.6%だけなら234円だが、日本の現行課税を10%とした処理費支出は257.4円相当、運営残642.6円で **Connect費等の控除前**。課税・端数は実請求書に従う。運営管理の料金モデルは月に入金したシッター1人200円+入金1回250円+入金額0.25%（各税前）。月10件を同じシッターへ4回入金する例では、fee9,000円から処理/Connect税込概算4,048円を引き4,952円。他の事業費控除前であり、全シッターの予約分布・回数から再積算する。旧「900−234=666円」を最終利益に使わない。

上記はRadar追加費を含まない基礎試算。Managed Risk自体はlisted Payments/Connect価格なら追加なしという説明だが、必須Radarの必要tierと日本の適用費は未確認。現行日本料金には標準Payments込みのLiteと、platform Standardの8円/スクリーニング+175円/有効口座等が併記される。Standardを仮適用し1有効口座/月1件/入金1回なら、基礎試算の運営残132.2円から税込相当201.3円を引いて**−69.1円**になる。失敗/遮断も課金対象になり得る。Liteで足りると断定せず必要tier・active定義・税・実スクリーニング数をG05で確認する。決済の従量費はソフト月5,000円と別枠でも、15%の採算には必ず含める。[決済調査 v0.2補足](../research/TECH-PAYMENTS.md)、[Radar日本料金](https://stripe.com/jp/radar/pricing)

初期入金は週次を推奨する。月次にして費用を減らすことだけでシッターの資金繰りを悪化させない。支払成功と銀行着金予定/失敗を別表示。口座への即時入金は保証しない。

**運営の損失責任を小さくするManaged Risk構成を先に確認し、Expressへの好みを理由に運営の負残高責任を既定にしない。** 候補は次の3つ。どの構成も日本の業種/個人事業シッター/後払い/実費/取消料/返金/閉鎖に対する適格性を未確認のため、G05/D1で条件を確定する。

| 損失/画面の候補 | 判断と未確認条件 |
|---|---|
| fees=application + losses=stripe + dashboard=none | **損失責任を抑える第一確認候補**。Managed Riskは直接決済/Radar/card_payments/full契約等が必要。hosted/embedded onboardingに加え、Notifications BannerとAccount Management等のStripe embedded componentsを接続し、追加KYC/口座変更を自社原本回収なしで処理できるか確認。JPでの提供/料金/義務を確認するまで確定しない |
| fees=application + losses=application + dashboard=express | 文書化された代替。外部管理画面で運営実装を減らせるが、回収不能負残高・留保金等を運営が引受ける。損失上限/備え・返金原資をD1で明示判断する |
| fees=application + losses=stripe + dashboard=express | 公開preview条件があるため、初期GA前提にしない。提供/日本契約条件が揃った場合のみ再評価 |

カード受付に必要なfull service agreementとfull dashboardは別。full dashboard + fees=application はv1公式のunsupported構成で、v2の一般表だけから利用可能とは断定しない。**未払い報酬を立て替えない合意は、全ての決済損失責任がゼロという意味ではない。** Managed Riskでも運営自身の負残高・処理費等は残り、Stripeによるhold/停止/追加情報要求があり得る。85%+実費は配分原則で、返金/紛争/留保時まで同額着金を保証しない。アプリの新規受付/未払い制限と、外部口座の支払/入金停止や直接debitの権限を同一視しない。各構成の現金負担と利用者導線をD1に提示する。[controller制約](https://docs.stripe.com/connect/migrate-to-controller-properties)、[構成と必須components](https://docs.stripe.com/connect/design-an-integration)、[Managed Risk条件](https://docs.stripe.com/connect/risk-management/managed-risk)

予約時は外部画面で支払方法登録とoff-session同意。方法登録は入金保証や長期与信保持ではない。保護者×シッター単位で外部Customerを分離する案を初期とし、シッターごとの再登録のUXを明示する。実績/通知/異議と原子的に請求権を取得し、Webhookを署名検証して永続化、タイムアウト/順不同/重複を外部APIと照合する。追加認証は本人の再支払いへ案内し、勝手な自動再請求を追加しない。

PAY.JP Platformは費用候補だが、公開標準の口座原情報の自社回収、シッター控除の振込費、閉鎖時少額残高の扱いが現要件と衝突するため第一候補にしない。解消を確認したときだけ再評価する。直接入金だから法令上の確認不要とは断定しない。

## 7. 初期AIの具体案

**OpenAI APIのgpt-6-lunaを、サーバーの交換可能adapterから呼ぶ評価候補にする。** 自己紹介の下書き/校正、公開済み規約FAQ、個人情報を送らない申請不足案内で日本語品質・遅延・誤案内を評価する。Responses APIをHTTPSで使用し、JSON schemaの出力を再検査。FAQは公開規約をDBから検索し根拠節IDを付け、根拠がなければ回答せず運営へ渡す。専用vector DBやモデルの外部Web検索を初期必須にしない。採用はアカウント提供条件/データ委託条件/評価が揃ってからで、有料API利用を今回開始しない。

確認した短文Standardの公表単価は入力$0.10/100万token、出力$0.50/100万token。平均入力2,000・出力（reasoningを含む課金token）1,000、月1,000回なら$0.70、150円/ドル+税相当10%で約116円。キャッシュ作成等を使う場合の追加費は別。これは試算であり日本語文字数=token数としない。実token・再試行・失敗呼出を台帳へ記録し、公開前に評価値で更新する。gpt-5.4-nanoは廃止告知済みのため新規第一候補にしない。[モデルと単価](https://developers.openai.com/api/docs/models/gpt-6-luna)、[廃止予定](https://developers.openai.com/api/docs/deprecations)

上限は月1,000円。最大入力/出力、1人/日頻度、同時実行数を制限し、呼出前に最大見込額をDBで原子的に予約、終了後に実額へ精算する。in-flightの留保も含め予算不足なら実行しない。料金/為替表に版を付け、50/80/100%通知。事業者dashboardの予算通知だけをhard stopとみなさない。AI障害/予算切れでもフォーム・定型FAQで通常予約/確定データ閲覧を継続する。

store=false、外部ツールなし、会話の恒久保存なしを初期設定案とする。ただしstore=falseは全ログ即消去ではなく、標準のabuse監視保存等が残る。APIデータは明示opt-inがなければ学習不使用という説明と、委託/保存/地域条件を区別する。身分証・資格原画像/番号・住所・医療画像・事故本文・決済情報を初期AIへ送らない。文章の内容確認と公開は本人が行う。審査疑義/医療/予約/金額/処分をモデルだけで確定しない。[データ取扱い](https://developers.openai.com/api/docs/guides/your-data)

公式にはaliasのみ示されるため存在しない日付snapshotを捏造しない。実際に返るmodel名・prompt/規則/根拠版を記録し、更新時は合成評価セットで比較する。資格OCRと詳細運営AIはG27の評価後であり、初期AIをまとめて後回しにしない。

## 8. 情報保存・画像・復旧

TokyoはDB配置の選択で、Auth/Edge/ログ/メール/AI/再委託先まで全て日本国内で完結する保証ではない。各データの流れ・保存地域・国外処理・DPA/再委託先・削除/開示・秘密管理をG04で確認する。地域条件が不適合なら保存先を再選定する。[基盤調査](../research/TECH-INFRA.md)

private bucketでも権限設計がなければ安全ではない。用途別ACLと報告者/審査/事故/決済担当を分け、運営MFA aal2・現在role・セッション有効性をAPI/DBで検査する。期限URLは短期bearerとしてログ/メールへ含めず、メールは詳細本文でなく認証後の画面を案内する。発行済URLはAuth key/role変更で直ちに失効するとはせず、期限とcacheの残存窓を試験。資格/医療/事故等の厳格な原本は毎回認可する配信経路を選び、private/no-storeにする。既に利用者が取得した画像の端末内複製を遠隔消去できるとは説明しない。添付は拡張子だけでなくmagic bytes・容量・解像度・decodeを確認し、HTML/SVG等の実行コンテンツを拒否。位置情報/不要metadataをサーバーで除去して再encodeする。ブラウザー側除去だけを保証にしない。Deno制限内での画像処理・安全な隔離/公開可否をPoCで確認し、不成立なら処理用サービスと費用を具体化する。

DB日次backupの保持と別に、Storage原本は別アカウント/資格情報の非公開backup先へ12時間単位で増分コピーする。第一候補はAmazon S3 Tokyo。調査時のStandard先50TBは$0.025/GB月で10GB月なら保存のみ$0.25。第5章はこれに操作/取り出し/世代増を加えた予算枠。対象manifest（object ID、hash、版、種別、権限参照）とDB snapshotを照合し、暗号化・鍵/復号権限・backup失敗監視を設計する。単に同じbucketへ複製したことを独立backupと呼ばない。保存量/変更分/操作/取り出し/転送・鍵費を積算し第5章の枠に収まるか確認。事業者の標準backupが全障害を防ぐとはしない。

資格/届出/保険原本、児/住所、会話、医療、事故、取引証拠、監査/会計を別の保存期間表へ。目的・起算点・閲覧期限・消去期限・法的保全・外部委託/backup期限をD4で判断する。30日一律削除は確定しない。論理削除/保全状態を復元後にも適用し、削除対象がbackup復元で利用者画面へ再出現しない手順を持つ。今ターンに削除や期間の強制適用はしない。

RPO24時間/RTO24時間は目標で、今回達成未検証。DBと原本を別の合成環境へ復元し、ログイン/鍵/権限/署名URL/予約/取引照合まで試す。失われた決済受信イベントはStripe API等から照合する。復元完了まで外部送信/請求を停止でき、再開時に重複送信しないことが必要。

## 11. 既存Node/JSONからの移行順

今回ソース・DB・データの変更は行わない。後続はローカル実装の許可と高リスク/外部操作の境界を照合して進める。

1. 現行package-lockとruntime、API入出力/エラー/料金例・保存形式schema:1を記録。server.mjsの業務計算とNode HTTP/fs境界を分ける計画を作る。UIのUX01〜09とプロフィール/週次例外の資産を維持。
2. G01で業務型、API版、料金snapshot/同意版、冪等キー、定期回別/変更/実績/例外の契約を確定。既存合成テストを契約テストとして保存し、同時処理や権限の意味のある試験を追加する。
3. local Supabase等に空の**別環境**を作り、追加型SQL migrationでschema/制約/索引/RLS/DB関数を構築。既存JSONは読み取り元の複製として保持し、reset/削除/強制上書きしない。migration生成/適用はその時点の公式CLI手順と許可に従う。
4. JSON→local合成DB importerをdry-runし、ID対応表・件数/金額/時刻/hash・参照欠損を照合。重複importの冪等性、失敗rollbackを確認。元ファイルは残す。**現在のJSONは合成デモなので本番へ投入しない**。審査済fixture・x-demo-actor切替・合成児を本番認証/審査へ変換しない。
5. pureな料金/年齢/JSTロジックをTypeScriptへ段階移植し、既存Node検証とDeno検証で同じ契約例を比較。Node fs/lock/HTTPをrepository/API adapterで置き換える。SQL transactionが公開時の正本となり、単一プロセスのJS queueだけに依存しない。
6. UIはAPI clientのURL/認証adapterを切替え、料金/入力/エラー互換を確認。デモactorと本番Authの環境を明確に分離。最新権限、aal2、セッション、私有添付の迂回試験を行う。段階公開する場合も本番の二重書込を無造作に導入しない。
7. local合成で全フローを接続後、別許可のクラウド/sandboxでPoCと復元を実施。本番は新規利用者の正規登録から始める。将来実データ移行が必要な場合だけ、対象・停止時間・backup/差分・照合・切替/戻しを版固定して別承認する。
8. 旧/新APIの互換期間と切戻しを設計。expand/contractで先に読取互換を残し、戻しても新データを失わない。課金/メールoutboxは切替時に送信主体を一つにし、旧worker再起動で二重発火しない。不可逆のdown migration/DB resetをロールバック手段にしない。

依存はlatestを固定版へ変えlockfileを維持し、npm ci・typecheck/build/node:testとDeno/SQL統合をCIへ。Node/Vite/Reactの対応組合せは採用時公式条件と現lockを照合して固定し、今日のlatestへ自動全面更新しない。Deno依存とSupabase CLIも版管理。DB/Edgeのmanaged runtime更新は監視対象とし、changelogのTLS/索引変更等を確認して重要テストを再実行する。

PWAはmanifest/ホーム画面導線を追加し、service workerは公開static shellだけを対象にする。医療/児/住所/事故・認証応答を永続cacheしない。オフライン/再接続で予約成功を偽表示しない。iOS Safari/Android Chrome/desktop、375px、キーボード/ラベル/色に依存しないエラー表示をG23で実証する。
