## 目的と採用範囲
合成登録後に自分の情報を整え、保護者が登録児を依頼条件へ選び、シッターが自分の時給と受付時間を変更し、その変更が検索・新規依頼・承認へ一貫して反映される増分を作る。親が把握する2026-10-17の「では、その先の実装も引き続きやっちゃってください」がローカル実装の根拠。通常設計は委任済み。既存の独立監査工程を通す。
お気に入り・相談一覧は今回入れない。既存相談・正式依頼・交通費相互確認と予約一覧を保持する。実個人情報、連絡先、番地、健康情報、画像、書類、認証・審査管理、削除、決済、メール、外部公開は対象外。プロフィールは合成表示名・地域と合成児の呼び名・生年月日のみ。

## 所有者API・入力境界（NC06）
GET /api/me を追加しactor本人の編集用射影だけを返す。自己情報の参照はtarget IDを受けずactorから求める。bootstrapは全利用者の切替用id/role/nameと公開シッター情報を返し、他保護者のchildrenを含めない。自分の児は /me 経由とする。公開シッターには表示に必要な地域・料金・資格・年齢・人数・受付時間だけを返し、審査原本やreviewの内部値は公開しない。
- PATCH /api/me: {name, region, expectedRevision, operationId}。nameはtrim後1〜40字の合成表示名、regionはデモ3地域。表示名の合成ラベルは重複付与しない。
- POST /api/me/children: {name, birthDate, expectedRevision, operationId}。
- PATCH /api/me/children/:id: 同上。保護者本人の既存児だけ。未知/他人のIDは404。シッターは403。
- PATCH /api/me/sitter-settings: {rate, availabilitySchedule, expectedRevision, operationId}。シッター本人だけ。保護者は403。
児の生年月日は実在するYYYY-MM-DD、日本時間の今日以前、1900-01-01以降。nameはtrim後1〜40字。サービスの年齢適合をプロフィール保存条件に混ぜない。
許可フィールドを明示検査し、role/id/children配列/review/qualifications/ageMonths/capacity/multiScenario/available/transport等の自己昇格や無関係フィールドは422。入力オブジェクトをユーザーへspreadしない。審査済みfixtureの確認フラグも、新規シッターのfalseも更新不可。料金・空き時間の保存成功で新規シッターを掲載/受付可能にしない。
既存のactor当事者検査、loopback/Host/Origin/JSON制約を維持する。

## 受付時間（NC07）
新しい任意フィールド availabilitySchedule = {weekly: [7 entries], exceptions: {YYYY-MM-DD: entry}}。weeklyは日曜0〜土曜6の長さ7固定。entryはnull（休み）または {startMinute,endMinute}。分は整数・15分倍数、0 <= start < end <= 1440。startは0〜1425、endの1440は24:00表示。例外は実在日、最大60件、同一日は1件。空配列や不明なキー、逆転、重複日入力、文字列の分、15分外は422。
現段階は同一日本日内の1連続枠だけ。終了が翌日00:00のときだけ前日のendMinute=1440として判定可能。日跨ぎの複数枠接続は行わず、画面にも翌日へ跨ぐ枠は別対応と明記する。
旧データは新フィールドがなければ従来availability（8:00〜22:00等）を毎日に適用。旧availabilityも無い場合は従来と同じ毎日0〜24時。読み取りで合成した既定値は既存ファイルへ一括保存しない。保存後はavailabilitySchedule優先、古いavailabilityは互換用に残せる。
共通の受付判定を検索、新規依頼、承認へ適用し、スケジュールから外れれば候補除外/OUTSIDE_AVAILABILITY。承認時点の設定を、既存のStore.mutate内で競合検査・保存まで直列化する。成立予約の重複と30分余裕の既存検査は継続。休みに変更しても成立予約の日時・状態・金額は変えない。既存成立予約は予約一覧に残す。移動余裕の編集は今回対象外。

## 価格・スナップショット・互換性（NC08）
現在のPOST /requestsは送信時にサーバーで再計算するため、料金編集を加えるだけでは表示済み概算と異なる金額で依頼を作れる。この隙間を今回必ず閉じる。
- /quotesは従来同様quote.rateを返す。UIはその表示済み概算のrateをexpectedRateとして正式依頼に送る。新しい未処理の正式依頼では必須、整数かつ現在時給と同じことを検査。不一致は409 PRICE_CHANGED、未指定/型不正は422。値上げ・値下げどちらも同じ。金額は引続き全てサーバー計算し、expectedRateを料金の代替入力にしない。
- PRICE_CHANGEDでは送信成功扱いにせず、入力・相手・相談を保持し、旧概算/同意を無効化して再見積りへ誘導。条件を変えず通信だけ失敗した再送は同じoperationId/本文を使用する。
- 正式依頼のquote/children/交通費/規則版は作成時スナップショット。pendingも以後の料金や児プロフィール変更では書換えない。承認では現在の資格等・利用日時年齢・受付時間・重複/余裕だけを再検査し、保存済みquoteを予約へ引継ぐ。current rateで計算した結果を保存済み価格へ代入しない。
- 新規則版を更新する。schemaは1のまま、userの任意profileRevision（未保存は0）とavailabilityScheduleを追加するだけ。既存users/requests/bookings/messages/operationsを初期化・移行削除しない。
- 既存成功operationIdの同内容再送を、expectedRate等の新しい必須検査より先に返す。既存fingerprint方式を変更しない。旧承認再送・交通費規則前の旧pendingも維持し、旧数値料金を再計算で置換しない。

## 原子的更新・再試行・競合（NC09）
新更新もStore.mutate/persistを経由し、保存成功後だけメモリ/成功応答へ反映。operationはactor+operationIdをキーとし、フィンガープリントには操作種別・対象児ID・本文（expectedRevision含む）を含める。同一ID異内容は409。成功したプロフィール更新の再送は現在revisionの検査より先に元の結果を返す。保存失敗時は児/設定/revision/operation結果の全てが残らず、同じIDで再試行できる。
任意profileRevisionはプロフィール・児・料金空き時間を更新するたび+1。expectedRevisionは非負整数必須。現値と違えば409 PROFILE_CONFLICT。古い画面から無言で上書きせず、未保存入力を保ち最新情報の読直しを案内する。通常の読取ポーリングは編集中草稿を置換しない。
actor切替、画面アンマウント、編集内容変更をまたぐ遅い成功/失敗を新actorや新草稿へ反映しない。操作中は同じフォームの送信を抑止し、応答喪失再試行のoperationIdを保持。新しい編集または競合解消後の送信には新IDを使用する。

## 実装構造と検証
新しい依存・サービスは不要。server.mjsのHTTP/Store/既存operationは維持し、プロフィールの許可項目検査と受付時間の純粋関数を小さなserver側モジュール（例 profile-domain.mjs）へ分離。全体のHTTP設計を作り直さない。画面は自己プロフィール/児編集/料金空き時間のコンポーネントをsrcへ分け、main.tsxはナビ・actor文脈・既存予約フローを接続する。API型と状態遷移を小さく共有し、既存quote-stateを再利用する。
