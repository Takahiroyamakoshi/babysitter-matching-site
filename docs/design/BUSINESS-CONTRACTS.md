# 業務契約 G01
版: 0.1（独立設計・計画監査待ち） / 更新日: 2026-10-17
基準: [REQUIREMENTS v0.45](REQUIREMENTS.md) §29/30優先、[製品完成条件 v0.2](PRODUCT-COMPLETION.md)、[全体計画 v0.2](../IMPLEMENTATION-CHECKLIST.md)、[技術選定](TECH-STACK.md)。
対象: Lの合成実装からRへ引き継ぐ状態・データ・アクセス・同意・通知・再試行の契約。既合意を通常設計へ具体化する。文書完成は機能実装・制度適合・D1〜D4決定・公開合格を意味しない。外部アカウント/実情報/メール/決済/削除/公開の実行許可を追加しない。

## 1. 共通値と不変条件（BC01）
- IDは安定した不透明値。所有者、担当者、予約回、実績版を各記録へ保持する。日時はUTCのoffset付き値で保存し、表示・暦日・月計算はAsia/Tokyo。clientの時計・金額・役割・成功自己申告を正本にしない。
- `revision`は集約の更新ごとに増やす。更新は期待revisionと現在値を照合。古い画面へ409と最新revisionを返し、入力は保持する。新規操作IDで最新内容へ明示的に再確認する。
- 予約、審査、実績確認、請求、決済、銀行入金は別状態。保育終了を「支払済み」、通知保存を「メール到達」、資格確認を「本人確認済み」と表示しない。
- 業務更新・監査イベント・outbox・冪等結果を一体保存し、保存完了後だけ成功を返す。Lは既存Storeの単一writer/候補clone/永続化後切替、RはDB transactionと共通guardで保証・実証する。L合格で分散DB原子性を証明しない。
- 審査・入金準備・年齢/地域/人数適合・未払い制限を画面とAPIの作成/承認/変更/開始で再検査。医療系は全経路で受付無効。適合の証拠不足は不可、合成の適合flagを本番証拠へ移さない。
- 既に保育中なら未払いだけを理由に終了を強制せず、安全な引渡しを継続し運営へ連絡。報酬没収・代替手配・常時即応の保証を追加しない。

## 2. 記録と入出力（BC02）
実装は以下の論理記録を持つ。全てを一度にDBテーブル化する指示ではない。共通にID、revision、作成/更新時刻、必要な監査参照を持ち、秘密・原本・カード情報をイベント本文へ複製しない。

| 記録 / 後続担当 | 最小データと入力→出力 |
|---|---|
| Account / G06 | login主体、現在role/利用状態、公開名、連絡参照。認証結果→現在の権限。児/訪問先/緊急連絡先は本人の私有記録として分離 |
| SitterApplication / G07 | 資格/研修/届出/初回保険の項目・private原本参照・版・有効期間・確認根拠/担当/時刻。提出→掲載/受付可否。保険更新と初回確認を分離 |
| PayoutReadiness / G17a | 事業者account参照、未完了/確認要/準備完了、検証時刻/根拠。外部結果→受付ゲート。原本人確認資料は外部事業者が扱いアプリは代理取得しない |
| PublicProfile / Schedule / Favorite / G08 | 公開最小projection、地域/対応年齢人数/資格/サービス/単価版、週次枠/日例外/本人調整buffer。本人設定→検索結果。お気に入りは保護者×シッター一意 |
| Conversation / Attachment / G09 | 当事者2ID、message ID/順序/本文/時刻、添付種別/所有者/ACL/処理状態。相談→会話、予約成立作用なし。未送信草稿と永続messageを区別 |
| QuoteSnapshot / Consent / G11〜15 | 条件hash、サービス/児の利用時情報、日時/単価/料金規則版/取消規則版、内訳/実費、合計、税取扱状態、各当事者/時刻/対象版。同意対象を表示→固定見積り。住所等の不要複製なし |
| Request / Booking / G11〜15 | 依頼/予約ID、当事者、期限、成立版、確保時間、buffer、見積り/同意参照、service、定期series/occurrence ID。承認→1依頼1予約。成立後も元依頼を保持 |
| ChangeProposal / G15 | 元予約revision、提案条件/追加額/取消影響、双方の同意、期限/状態。双方承認→予約新revision。未承認時は元予約を保持 |
| ServiceEvent / ActualReport / Dispute / G16 | 予約/実績版、開始終了の実績時刻と操作時刻/担当、承認済変更、内訳/実費証憑参照、確認状態、通知成立時刻、異議/合意参照、明示承認必須flag。報告→確認対象の不変版 |
| Settlement / PaymentAttempt / Payout / Refund / G17b | 予約+実績版の確定額、請求原因/同意、事業者冪等key/account/environment、試行/イベントID/照合結果、追加認証参照、入金/返金額。確定額→外部照合済結果。カード/口座原情報なし |
| Debt / Cancellation / Exemption / Action / G18〜19 | 残債原因/額/結果、取消主体/理由/発効時刻/計算基礎/料率、証跡/免除判断、処分根拠/人の確認。未払い→全予約制限。制裁として他報酬を控除しない |
| Incident / SupportCase / G20 | 予約/報告者/role、発生時刻・状況・児状態・対応・連絡状況、任意写真、緊急度/担当/状態/連絡履歴。保護者の連絡欄はシッターとの連絡状況。双方の報告を独立ID/ACLで保存 |
| Review / Moderation / G21 | 利用/決済済予約ID、投稿者/公開名/星1〜5/本文/返信/投稿編集時刻、通報/非公開理由履歴。1予約1件、投稿期限30日・期限内編集。期限起算の通常設計はG21で具体化し、今回の実装範囲へ加えない |
| Notification / Outbox / Audit / G10・23 | event ID、種別/対象ID+版/受信者、channel別状態/時刻/送信ID/試行/次回/lease、Web既読時刻、actor/操作/結果。業務状態→再開可能な通知。機微本文・bearer URLをメール/ログへ転記しない |

保存期間は種類別に目的/起算/閲覧期限/消去期限/法的保全/外部・backup残存をG04/D4で確定する。ここでは一律の年数・医療30日削除を作らない。退会/非公開化と物理消去は別。復元でも保全・取消・削除対象の利用制限を再適用する。

## 3. 状態遷移（BC03）
状態名はAPI契約の意味を示す。現在の `requests.status=confirmed` / `bookings.status=confirmed` を破壊的renameせず互換adapterで読めるようにする。

| 集約 | 許可する遷移 / 主体・条件 |
|---|---|
| Account | 登録→active（審査済とは別）。退会申請→closing（新規停止）→closed（残予約/精算/異議/事故を整理）。処分は別記録、人の確認が必要な措置を自己編集/AIで決定しない。closedでも必要な残務用の限定アクセスをG04/G06/G19で定義 |
| Application | draft→submitted→needs_resubmission / under_review→verified / not_accepted。本人は提出/再提出だけ。疑義を自動合格にしない。資格・届出の確認状態を別表示。初回確認済の保険更新待ち/期限切れを自動受付停止へ結び付けない |
| Request | pending→confirmed / declined / expired。保護者送信、相手シッターだけ承認/辞退。`expiresAt=min(sentAt+24h,start)`、`now>=expiresAt`は承認不可。チャット返信/通知成功で成立しない |
| Booking | confirmed→in_progress→ended、未実施はcancelledへ。担当シッターが開始/終了。実績時刻と操作時刻を別保存。開始予定前の開始を拒否、未払いを開始時検査。終了した事実で未承認の短縮減額/延長課金を作らない |
| Regular | seriesは先4週間を提示、各occurrenceにRequest/Bookingを持つ。一括承認は回別の成功/競合/期限を返す。失敗回を暗黙再予約せず再確認、成功回の取消/精算は独立。ペナルティ一括集計はD3留保 |
| Change / Extension | proposed→accepted / declined / superseded。延長は保護者申請/シッター承認、15分単位・追加額提示。条件/日時変更は双方同意と現在適合・枠検査。提案が古ければ409。短縮は元取消影響と新見積りも双方確認 |
| ActualReport | draft→awaiting_notification→awaiting_guardian→approved / superseded / disputed。通常訂正は新実績版と再通知。未報告は料金未確定のまま通知。報告期限超過だけで拒絶/自動請求しない |
| Dispute | open→discussing→support_requested（未解決時）→resubmitted→resolved。まず当事者チャット、必要時運営。異議後は履歴を保持し `requiresExplicitApproval=true` を以後の版へ継承。再提出の受理だけで解決/決済にせず、保護者の当該版明示承認で精算可能。長期未承認の強制終了はD3 |
| Settlement | none→ready→processing→succeeded / requires_action / failed / unknown。readyは当該実績版の明示承認またはBC06の自動条件だけ。processing/unknownは外部照合まで訂正/異議で未確定へ巻き戻さない。既決済の異議は返金相談へ。再試行の新請求を自動発行しない |
| Payout / Refund | 請求成功と入金予定/入金完了を分離。返金はrequested→under_review→processing→succeeded / failed / unknown。当事者合意/根拠+運営確認後だけ外部処理。チャージバックと返金は別イベントで残高照合、費用負担D1留保 |
| Incident / Support | incidentは未対応→対応中→対応完了。受付担当が事実確認/案内/必要な指導・再発防止を終えた状態。治療/保険金完了とは別。完了の報告者自動通知なし。問い合わせは受付/担当/対応状態/引継ぎを持ち、応答時間やAI最終判断を追加しない |
| Review | 投稿→編集（期限内）/通報→権限運営が理由付き非公開化。低評価だけで削除しない。利用/決済なし・他人/二重投稿を拒否 |

終了記録で予約の合意済確保区間を黙って短縮しない。枠の重複検査は未実施/実施中の予約と保持すべき元区間を参照し、状態名追加で従来の `confirmed` だけを検査する穴を作らない。

## 4. アクセス・公開・同意（BC04）
全てserver側で現在actor/所有権/role/セッションを検査し、拒否時の応答に他人の本文を含めない。Rの運営操作はMFA必須。Lの `x-demo-actor` は合成認証であることを明示する。

| 情報/操作 | 未ログイン | 本人/予約当事者 | 審査担当 | 事故/問い合わせ担当 | 決済/処分担当 |
|---|---|---|---|---|---|
| 公開プロフィール/空き枠/公開レビュー | 最小公開のみ | 同左、本人は許可項目編集 | 公開内容/確認表示管理 | 公開内容/必要な非公開化 | 必要な公開内容 |
| 児/訪問先/緊急連絡先 | 不可 | 保護者本人、選択した相手/正式依頼受信者へ必要範囲のみ。番地を検索者へ公開しない | 原則不可 | 対応caseに必要な最小範囲、アクセス履歴 | 原則不可 |
| 資格/研修/届出/保険の原本・状態・期限 | 不可 | 提出者本人。相手へ原本/保険情報を公開しない | 担当審査範囲のみ、確認根拠を記録 | ケース対応に必要な権限を別途確認、roleだけで全原本を読めない | 不可 |
| 相談/添付、予約/変更/実績/金額 | 不可 | 当該当事者だけ。保護者表示は総支払額、シッターは15%/手取り/実費も表示 | 相談本文は不可 | 相談依頼に必要な範囲を記録/監査して確認 | 精算異議・取引に必要な範囲のみ |
| 事故本文/写真/連絡履歴 | 不可 | 報告者本人のみ。相手当事者にも不可 | 不可 | 担当権限ありだけ。相手事実確認は必要事項を別連絡 | 不可（事故roleの別付与なしに読めない） |
| 支払/入金/残債/返金/免除証跡 | 不可 | 本人の必要情報のみ。相手のカード/口座/他予約債務を出さない | 入金受付準備の可否だけ | 対応に必要な要約のみ | 担当業務の必要範囲。返金/免除/処分判断は理由と履歴 |
| お知らせ/草稿/既読 | 不可 | 宛先本人のみ。相手の通知失敗診断は機微情報を除き必要範囲 | 担当の監視要約のみ | 担当の監視要約のみ | 担当の監視要約のみ |

公開projectionと本人projectionを別に持つ。添付は用途/予約/報告/actorへ結び付け、毎回認可する配信とprivate/no-storeを厳格原本へ適用。URL・ファイル名・object IDが分かっても権限を迂回できない。拡張子に頼らず形式/サイズ/画素/decode・metadata除去を検証し、不正な画像を公開しない。

同意は `actorId + action + subjectId/revision + conditionHash + quote/ruleVersion + acceptedAt` を保存。通常依頼の取消条件/交通費総額、承認時の同条件、延長追加額、変更/短縮、実績承認は別の同意。入力・対象児・日時・料金規則の変更は未送信概算/同意を失効。成立済snapshotはプロフィール/単価更新で変えない。古い同意や異議前の同意で新実績版を請求しない。

## 5. 料金・枠・取消（BC05）
- 通常3h以上/15分、上限10,000円/時、1〜3人と適合全条件。年齢は利用日で生後6か月〜小学3年度末、1歳未満は保育士/看護師。幼稚園教諭のみは必要研修。医療受付は無効のまま。
- 子ども/時間帯別に時給×時間×(1+該当児病児0.3+21〜翌8時の夜間0.2)を非丸め合計し円未満切捨て。病児計算契約は受付許可を意味しない。手数料=対象サービス/取消料×15%切捨て、差額がシッター。実費交通費/立替は対象外。税は適合確認前に一律決定しない。
- 別日面談は30分単位・人数/病児倍率なし、夜間20%/15%手数料。同日有料時間内面談は二重課金なし。徒歩/公共交通送迎は最低なし、開始=max(約束,実到着)〜事前登録相手への引渡し完了を実績1分単位、人数/夜間適用。タクシー/運転は無効。
- 交通費は合理的往復実費を事前提示/双方確認。未確定はnull、0は明示的合意額。立替は事前同意と証憑が必要。未承認延長/超過/争いのある追加額を自動料金に足さない。
- 依頼承認・延長/日時変更承認は当事者guardを一定順序で排他、現在の枠/適合/未払い/入金準備/期限を一体検査する。隣接の必要間隔は両予約bufferの最大値で、30分を双方分加算しない。本人buffer変更は成立済みへ無確認遡及しない。
- 保護者通常取消はJST開始日の前々日以前0%、前日50%、当日100%。成立見積りサービス料（病児/夜間含む）を基礎、発生済/返金不能実費だけ追加。シッター取消は保護者請求なし。取消時期はJST暦日で前々日以前0件、前日・当日1予約1件。定期一括取消も各回で時期判定し、理由/証跡/免除を保存。
- 未払い取消は別規則：開始24h前の未解消50%、24h前を過ぎてからの未払い発生は未実施対象を即時100%。job遅延時も本来判定時刻/当時の債務を参照し、実施中/済みへ二重料を付けない。全残債成功確認で制限解除、取消予約の自動復活なし。
- ペナルティは免除分を件数/起算から除き3件注意メール・4件退会勧告・5件強制退会。最終対象事象からJST暦月3か月問題なしでリセット（月末は到達月末へ丸める）。異議中措置保留、4/5件は人が確認。定期一括集計/加重/追加制裁はD3まで執行しない。

## 6. 通知・期限・精算起算（BC06）
基本はWeb内お知らせ+メール。関連画面への認証付きリンクと最小文面、未読/既読を保持。送信元・機微本文を全員へ一律転送しない。通知の重複keyは `eventType + subjectId + revision + recipientId + channel`。

| event / 起点 | 宛先・通知契約 / 失敗時 |
|---|---|
| 依頼送信/承認/辞退/失効、変更/延長提案と確定 | 操作対象の相手、成立/取消等の結果は必要な双方へWeb+メール。期限/枠の更新は通知失敗で巻き戻さずoutbox再試行。チャット新着は未読まとめ、相談への24h期限を追加しない |
| 保険期限30/7/0日前JST9時 | 対象シッターのみWeb+メール、有効証明書版/対象日別に各1件。停止後復旧時は期限までに到来した3回の未処理通知を重複なく処理し、本来日時/遅延を記録。期限後の追加反復を作らず、受付停止/保護者公開に使わない |
| 保育終了+24hで未報告 | 担当シッターへWeb+メール1件。報告が来れば未処理reminderを抑止。料金自動確定なし |
| 実績提出/通常訂正/異議後再提出 | 保護者へ当該版Web+メール。実績通知の成立はその版のWeb永続保存とメール事業者受付成功が両方揃った時点（後の時刻）。開封/既読は条件にしない。メール受付は端末到達の保証ではない |
| 決済失敗/追加認証、未払い制限/取消 | 保護者へWeb+メール、成立済予約担当者へ必要な制限/取消情報もWeb+メール。残債詳細を他シッターへ開示しない。再支払い導線。自動再請求の許可としない |
| 事故受付 | 保存直後、権限ある運営へWeb優先一覧+件名先頭「【緊急・事故報告】」のメール。写真なし可。送信障害は報告保存を維持し緊急配信失敗を監視/再試行。緊急対応を入力/運営返答待ちにしない |
| 事故対応完了 | 状態/監査だけ更新。報告者宛て完了自動お知らせ/メールを生成しない。必要な個別メールは担当者による別記録/別許可 |
| 審査不足/結果、取消免除/措置、退会残務 | 本人へ必要な根拠/行動をWeb+メール。原本をメール添付せず、重大措置は必要な人の確認後。応答時間・保険金・入金完了を保証する文面を作らない |

実績通知の片channel失敗/timeout不明では `notifiedAt=null`、自動起算しない。同じ版の再試行成功で初めて確定。通知が成立してもメール恒久失敗を決済開始前に検知したら自動条件を無効化し、再通知成功から起算する（履歴は消さない）。処理中/成功後は自動的に未請求へ戻さず照合/返金相談へ。訂正後に旧版の遅延メール結果が来ても現行版の起算点を変更しない。

自動精算readyは同一transactionで `currentReportVersion一致 AND awaiting_guardian AND notifiedAtあり AND now>=notifiedAt+24h AND requiresExplicitApproval=false AND openDisputeなし AND 未請求` を検査。明示承認も対象版/revision一致を検査。異議とready化は同じ集約を排他し、異議が先ならready/outboxを取消、readyでも外部処理開始前なら保留。外部処理開始が先なら照合中として扱い、成功済を保留と偽表示しない。異議後再提出は何時間経っても明示承認以外でreadyにならない。

## 7. 再送・停止・互換（BC07）
- mutationは現在の認可を先に行い、`actor + operationId` と入力fingerprintで成功結果を再送。同ID/同内容は元結果、別内容409。記録済成功は再実行しない。保存失敗は業務/履歴/outbox/operation全て未確定、同IDで再試行できる。
- workerは短いlease/試行数/nextAttemptAt/最終エラー、事業者送信IDを保持。既に成功したchannelは再送しない。timeoutの不明結果を成功扱いせず照合する。メールは外部との完全な一回だけ配信を保証せず、重複可能性と同通知IDで運用照合する。
- 決済は予約+精算版に一意な請求権、事業者冪等key、イベントID一意を持つ。署名・生body・account・test/live環境を検査し、順不同/遅延/不明はAPI照合。failed/requires_action後は本人の手動再支払い。外部の実際の成功が確定するまで `succeeded` にしない。
- UIは確定済状態と草稿を分ける。失敗/409/オフラインで入力保持、偽成功なし。相手/actor切替前の遅延応答を新画面へ混入させず、同内容再送は同operationId。再読込で保存済状態から再開できる。
- API新規業務はcontractVersionを持ち、同じ `/api` に追加型で実装可。後の互換破壊時は明示version/adapterを用意。既存エラーcodeと既成功operation fingerprint/結果を勝手に書換えない。
- schema:1の元JSON・ID・messages/requests/bookings/operationsを保持。新コレクション/booking revision欠如は読取時の既定値で扱い、既存confirmed予約を未実施と読む。旧quoteの税未検証/欠ける同意履歴は「legacy synthetic」と明示し、同意/実決済を捏造しない。
- 古い成功依頼/承認を新必須fieldで拒否しない。新機能への書込は当該新契約の検査後だけ。旧runtimeへの無造作な切戻しで新fieldを消さず、旧APIを維持した前進修正を基本とする。移行は別複製/dry-run/件数・ID・hash/復元比較、元削除/reset/強制上書きをしない。
- 合成fixture/外部代替はtest/local明示。新環境に審査済flag/actor偽装/合成児を本番登録として輸入しない。試験用clock/故障注入を本番公開APIへ追加しない。

## 過払い返還の追加合意（2026-10-17、要件v0.47）

## 一部返金の分担確定（2026-10-17、要件v0.49）
一部返金では、減額する運営手数料対象料金に対応する15%の運営手数料も返還し、残額をシッター負担分とする（2026-10-17合意）。対象料金2,000円の減額なら、保護者へ2,000円を返金し、運営手数料返還300円・シッターへの返還請求1,700円とする。運営手数料対象外の実費交通費・立替費用の返金には15%を掛けず、その費目の返還額をシッター負担分に含める。戻らない決済手数料は運営負担とし、シッターへの返還請求に上乗せしない。
設計上の端数処理は既存の手数料切捨て規則と整合させ、元の手数料と返金後の対象料金で再計算した手数料との差額を、累計の運営手数料返還額とする。追加の一部返金では既返還額との差額のみを返し、複数回の返金でも全額返金時に元の手数料が全額戻るよう照合する。シッター負担分は累計の保護者返金額から累計の運営手数料返還額を引いて計算し、既回収額を差し引いて残額を管理する。Stripeでの具体的な返還API・資金計上順序はG05/G17bで確認する。
過去の一部返金算定の未決記述は、本合意の範囲で解消する。回収前の保護者返金は運営が原資負担する既合意を維持し、実装・実取引の完了とは扱わない。

シッターの取消ペナルティの時期区分は、保護者の通常キャンセルと同じ日本時間の暦日基準とする（2026-10-17合意）。保育開始日の前々日以前は0件、前日・当日は対象予約1件につきペナルティ1件。前日と当日で件数を加重せず、金銭徴収もしない。定期予約を一括取消する場合も各回の開始日と取消日時から個別に判定し、対象外の翌週以降を件数に含めない。例えば火曜日に当日分と翌週以降4回をまとめて取り消す場合、免除がなければ当日分の1件のみ。急病・災害等の証跡付き免除、依頼辞退・期限失効等の対象外条件は維持する。
