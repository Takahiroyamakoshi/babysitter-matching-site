## 1. チェックリストの使い方
- 状態は「計画」「設計監査済」「実装中」「検証中」「独立合格」「条件待ち」をタスク単位で記録する。G00は計画作成・独立監査完了、G01以降は計画または条件待ち。計画の合格を製品機能の完了と数えず、進捗率は付けない。親が担当/版/証拠/再開点を個別TASKへ記録する。
- Lは合成データと外部代替によるローカル実証、Rは初期公開に必要な機能/運用、Cは安全条件成立後の追加提供、Oは評価後の追加。全体要件と今の工程は別。通常のローカル実装の既存許可は継続し、全タスクの再許可は求めない。今ターンは全体計画を提示し、ユーザーが具体案を確認できる状態を先に作る。
- 将来実装タスクは本表の要件/依存/完了条件を個別TASKへ展開し、担当、state_version、対象版、試行、検証/レビュー参照を持つ。設計監査・ユーザー計画提示を経て対象増分を具体化する。外部操作、実情報、支出、公開、削除等は対象操作の明示承認を別に得る。
- 各タスクは実装担当の単体検証→独立したAPI/実画面/運用検証→成果物レビューを同一対象版へ揃えて合格する。調査タスクは出典日・適用条件・結論・不一致/選択肢を成果物として独立監査する。
- 下記「必要証拠」は将来の提出条件。未実行を合格とせず、持ち越しは無変更差分/ハッシュと影響確認を記録する。文書だけの修正で不要な製品試験を反復しない。

## 3. 実施の順序
1. G00の全体計画監査・提示、G01の業務契約。G02/G03/G04/G05の適合調査を始め、必要な事業判断を4群にまとめる。

3. G11の通常予約を全体契約に接続し、G13/G14/G15の全サービス・回別予約・変更へ拡張する。
4. G16/G17b/G19→G18、G20/G21/G22で利用後と例外運営まで通す。各依存が合成実証だけならR合格へ繰り上げない。
5. G23/G24→G25で全体の安全・復旧・採算・運営・公開判定を行う。G26/G27は条件待ちで保持し、病児無効は初期公開でも検証する。

既存のNEXT-COREの「次はお気に入り」の順番を、そのまま全体の優先順位にはしない。公開の根幹を塞ぐ状態契約・制度/契約/保存・運営を先に可視化し、手戻りを減らす。
