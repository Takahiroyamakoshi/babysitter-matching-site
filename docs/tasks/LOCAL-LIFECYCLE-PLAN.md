## 1. 増分の境界と利用結果
保護者とシッターが同じ成立予約の詳細を開ける。シッターは開始→終了→実績を提出し、保護者はお知らせから実績・合意済み金額を確認して承認、または異議を申し立て同じ相談へ戻れる。通常未確認の24hと異議後の明示承認を区別し、最終的に一件の「精算待ち（ローカル検証・請求なし）」へ進める。サーバー再起動で予約・実績版・通知・異議・承認・精算待ちが残る。

Lでは通知のWeb保存と合成メールadapter受付を保存する。メールは送らず、カード/銀行/Stripeの接続も行わない。精算待ちは請求成功・決済済み・銀行入金済みを意味しない。未払い発生/全予約取消等は今回の状態へ偽って接続しない。

対象は既存で承認された合成通常単発（既存の適合条件内の1〜3人、通常/夜間、合意交通費を含む）。面談/送迎/定期/延長/日時変更/短縮/取消/事故/実書類/本番認証/運営UI/レビューは後続。G10/G12/G15/G17a等の全機能完成を待つ代わりに、次の合成境界を明示する。

| 依存 | 今回使う境界 / 持ち越し |
|---|---|
| G10 | 対象実績/未報告通知だけの永続outbox、Webお知らせ、合成mail受付、仮時計での再試行。汎用通知/保険/実送信は後続 |
| G11/G12 | 成立時quote/ruleVersion/双方交通費確認を固定。追加料金入力なし。開始終了の実績記録だけで成立額を増減しない。現レート/プロフィールを再計算に使わない |
| G13〜15 | 当該サービス/変更はまだ無効。未承認延長/短縮/立替等を報告内で料金化しない。これらを必要とする金額は今回受け付けず、相談案内を表示 |
| G16 | 通常単発の実施/実績版/通知/確認/異議後再提出まで。運営への相談は既存当事者チャットを保持し、未解決時の運営機能は未実装と明示。運営が解決済みと捏造しない |
| G17a/b / G18 | 合成認証/審査の既存デモを維持。外部入金/カード登録/実決済/残債の生成はしない。精算待ちを外部adapterへの将来入力として固定し、一実績版一件を保証 |

本番用DB/認証/外部adapterへの移植をこの増分の前提にせず、既存Store/API/UIを拡張する。ドメインを小モジュールへ分離するかは実装担当の判断。全面書換え/新しいクラウド依存追加は不要。

## 2. 実装タスク L1→L2→L3→L4
同じ増分内の順序であり、複数の新規製品タスクをまとめて完了扱いする意図ではない。

### L1 — 予約詳細と開始終了・保存の契約
- 予約一覧/詳細を両役割へ追加。bootstrapに既にあるbookingsを利用しても個別GETでもよい。本人当事者だけ返し、第三者/別シッターのID指定を拒否する。元requestを上書きしない。
- 担当シッターだけ `confirmed→in_progress→ended` を進める。開始予定前は拒否、サーバー現在時刻を操作日時として保存。実績開始/終了、actor、予約revisionを記録し、終了前の報告/開始前の終了・重複した別操作を拒否する。保護者は閲覧のみ。
- 実際の開始終了が予定とずれてもsnapshotの金額を自動変更しない。「未承認延長や短縮は今回の報告で料金変更できない」と説明する。終了記録を使って元予約の確保区間を黙って短縮しない。
- schema:1の既存confirmedは開始前/revision0として読める。既存fixture/store/operationsは保持、新規collection欠如は互換読取。成功再送・同ID別内容409、保存失敗で履歴/状態/operationが片残りしない。

### L2 — 実績版・Webお知らせと合成メール
- 担当シッターが終了後に実績の要約を入力して提出。予約条件/実績開始終了/固定料金と交通費/規則版を表示し、実績versionを保存。任意の金額・相手ID・通知成功時刻・承認済flagをbodyから受け付けない。
- 実績訂正は新versionと履歴、同意の再確認/旧版失効を保存する。今回は要約訂正を対象とし、元の開始終了イベントや成立額を直接書換えない。金額変更を必要とする申告は相談へ案内する。
- 保存と同transactionでWeb通知/outboxを作る。通知ID/受信者/実績版/channelの一意性、既読は宛先だけ。最低限お知らせ一覧/未読件数/関連予約リンクを画面に追加する。
- Web保存+合成mailの受付成功の後の時刻を当該版notifiedAtへ。合成adapterの一時失敗/不明・再試行を制御可能にし、片方だけ成功では起算しない。旧版の遅延応答は現行版へ適用しない。合成受付表示を実配信と書かない。
- 終了24hで未報告ならシッターへ一件の合成Web/mail通知、実績なしで自動精算待ちにしない。遅い報告は受付け、未報告だけで罰金/処分を作らない。
- 仮時計/失敗注入はin-process testや専用local起動設定で渡す。ブラウザー操作用にも合成時刻を確認可能にし、本番/公開APIに時刻改変・故障注入経路を追加しない。jobが動く頻度は実装判断だが、再起動/遅延後も永続dueAtで判定する。

### L3 — 保護者確認・異議・精算待ち
- 保護者だけが最新versionを明示承認/異議申立てできる。実績と総額を見た上で操作し、旧version/revisionの操作は409で再確認へ。シッターが自分の報告を承認する経路を作らない。
- 通常はBC06の通知成立+24h経過か明示承認で当該版の精算待ちを一件作る。請求原因（明示/24h）、対象version/金額/承認者・時刻または通知起算を保存。精算待ちを支払済みと表示しない。
- 異議申立てで自動条件と未処理の精算待ちを保留し、理由/提出者/時刻/対象版を保存。チャットへ戻る導線。精算待ちとの競合は同じStore mutationで順序化し、外部作用のない今回では異議後に有効なreadyを残さない。保留履歴は削除しない。
- 異議後、シッターはチャット等で合意した内容を参照して新実績を再提出できる。要約訂正/成立額同額の範囲、`requiresExplicitApproval`を以後の版にも保持する。再提出しただけで異議解決済みと表示せず、保護者が当該版を明示承認して初めて解決/精算待ちへ。長期未承認は保留継続、D3の強制終了を作らない。
- 同時承認/異議/24h job、同ID再送、複数端末の旧版操作でも、請求前の最終状態と履歴・通知が一致する。自動起算の訂正/無効化はBC06、ready後の通常訂正は現行readyを保留して新versionへ進める。今回processing/succeededを模擬成功へ自動遷移させない。

### L4 — 実画面・独立検証と提出
- 両役割の予約一覧/詳細、開始終了、実績要約/訂正、お知らせ、保護者承認/異議、既存チャットへの復帰、再提出/明示承認、精算待ちの状態を375px/1280pxで確認。
- 失敗時に草稿/操作IDを保持、再読込で保存済状態へ戻れる。actor切替/遅い応答で前actorの本文/成功を混入させず、ポーリングで編集中要約を消さない。色だけに依存しない状態/エラー、入力ラベルとキーボード導線。
- typecheck/build、既存server/quote-state/next-core試験と意味のあるlifecycle API/domain試験を実行。独立API検証と親CUAの証拠を同一ソース版へ固定し、成果物レビューへ。回帰に関係する範囲だけ追加試験する。
